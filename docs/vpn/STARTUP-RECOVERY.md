# Проверки запуска и восстановления VPN · 0.6.13

## Что установлено

Проверены два механизма, при которых интерфейс мог не соответствовать состоянию принадлежащего Capri ядра:

1. Успешный запуск службы с потерянным ответом pipe. Раньше менеджер отмечал владение службой только после ответа, поэтому обработчик ошибки не останавливал потенциально уже запущенное ядро. Теперь владение фиксируется до запроса, а ошибка выполняет подтверждаемую очистку через тот же защищённый канал.
2. HTTP `/version` может отвечать, даже когда Mihomo не открыл свой прокси или DNS. Готовность теперь требует TCP-прокси и, при включённом DNS, TCP+UDP DNS именно у PID запущенного ядра по таблицам Windows. Порт, занятый другой программой, не считается готовым ядром Capri. Локальный sidecar отправляет подтверждение готовности; служба подтверждает старт только после этой проверки.

Native `StartCore` также освобождает свой процесс и Windows Job Object при любой ошибке после запуска. Проверка не использует завершение процессов по имени.

## RED → GREEN

- `node --test scripts/test-vpn-startup.cjs`: до исправления потерянный ответ оставлял fixture `running=true`; после — ядро остановлено, повторный запуск проходит. Проверены отказ неподготовленного ядра и совместимость со старой службой с явным сообщением об обновлении.
- `node tools/test-vpn-startup-native.cjs --baseline`: на исходнике из HEAD до исправления ошибка запуска оставляла реальный дочерний fixture-процесс в незакрытом Job Object (`alive=true`, `cleared=false`). Тест завершает только созданные им процессы по сохранённым PID и проверенному пути.
- `node tools/test-vpn-startup-native.cjs`: после исправления — `alive=false`, `cleared=true`. Реальный закреплённый Mihomo без TUN проверен в трёх сценариях: свободные порты, занятый UDP DNS и занятый TCP-прокси. Во всех трёх `/version` отвечал; готовность подтверждена только в первом. При конфликте sidecar завершён, его порты освобождены, конкурирующие тестовые слушатели остались доступны.

Использовались отдельные временные каталоги, случайные loopback-порты и безвредные fixture-процессы. Установленная служба, рабочий VPN, автозапуск сторонних клиентов, реальные профили и маршруты не изменялись. Тесты core/routing, которым DNS не нужен, отключают его только в собственном процессе теста; отдельный native gate проверяет настоящий DNS TCP/UDP.

## Обновление

После установки Capri 0.6.13 открой **VPN → Служба и диагностика → Установить / обновить службу** и подтверди UAC. Установщик Electron сам по себе не заменяет уже установленный привилегированный компонент в `Program Files\CapriVPN`. Старый компонент остаётся совместимым, но журнал напоминает, что его проверка сетевой готовности ещё не обновлена.

## Что ещё проверить вручную

1. Отключить VPN через Capri, полностью выключить компьютер и включить его снова. Подключить Capri один раз, проверить выбранную локацию и реальные HTTPS-запросы.
2. Повторить с перезагрузкой Windows, с сетью, которая появляется с задержкой, и после сна/пробуждения.
3. Проверить фактическую готовность TUN-адаптера, маршруты, DNS и восстановление после обрыва; проверка собственных портов не доказывает системную маршрутизацию или отсутствие DNS-утечек.
4. Проверить аварийное завершение Capri: принадлежащее службе ядро должно отключиться после потери heartbeat, а sidecar — после закрытия канала владельца.

Полный сценарий на перезагруженном пользовательском компьютере здесь не выполнен. Наличие запущенной службы или локального прокси другого клиента не доказывает, что его TUN подключён или мешает Capri. Причина конкретного пользовательского сбоя после reboot не объявляется подтверждённой; исправлены воспроизводимые дефекты готовности и владения процессами. Одновременная активная системная маршрутизация несколькими VPN требует отдельной проверки и не заявляется исправленной.
